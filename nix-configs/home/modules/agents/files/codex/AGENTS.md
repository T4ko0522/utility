# 回答言語

- 入力された言語にかかわらず、常に日本語で回答してください。
- 内部的な思考はどの言語で行っても構いません。

# 自律的な修正の実行

- 自律的に修正してよいのは、ユーザーが明示的に指示 (明言) した時のみとする。
- それ以外の通常のやり取りでは、修正内容を提示して確認を得てから実行する。
- 要件や要望が不明確な場合は、実行に移す前に質問を重ねて曖昧な点を明確にする。

# サブエージェントとタスクの委任

- リファクタリング、レビュー、広範な調査、ウェブやドキュメントの検索など、サブエージェントが利用可能でタスクごとに独立したコンテキストを有効にできる場合、あるいはタスクを並行して実行したい場合は、サブエージェントを活用して処理を委任してください。
- 調査は `investigator`、実装は `coder`、テスト作成・実行は `tester`、不具合の再現・原因調査・修正は `debugger` に委任してください。
- 独立レビューは観点に応じて `code-reviewer`、`security-reviewer`、`architecture-reviewer`、`docs-reviewer`、`test-reviewer`、`dependency-reviewer`、`performance-reviewer` に委任してください。reviewer はファイルを変更しません。
- モデルと reasoning effort は各 agent の TOML 定義に従ってください。
- タスクに必要な役割だけを起動してください。複数の reviewer には異なる確認範囲を割り当て、主担当が重複する指摘と観点間のトレードオフを整理してください。
- 委任する際は、最初に各サブエージェントへ目的・担当範囲・完了条件・変更してよいファイルを明示する。独立した作業は並列に委任し、依存関係のある作業は前提となる成果物を確認してから着手する。
- 主担当はタスク分解、サブエージェント間の重複や競合の回避、成果物の統合、最終検証を担う。サブエージェントの報告をそのまま採用せず、差分と検証結果を確認する。
- 同一ファイルを複数のサブエージェントが編集する必要がある場合は、編集担当を 1 エージェントに限定する。ほかのエージェントには調査・提案・レビューを委任し、競合を防ぐ。
- 既存のサブエージェントへ追加依頼する場合は、可能なら同じエージェントに継続して依頼し、前提や成果物を引き継ぐ。
- 単純な 1 ファイル修正や、依存関係が強く分割しても効果がない作業では、不要にサブエージェントを起動しない。

# ドキュメントと技術文書の適正化

* README、`docs/`、設計書、ADR、API 仕様、運用手順などを作成・更新する際は、網羅性や文章量を目的化せず、想定読者が理解・判断・実行するために必要な情報だけを記述してください。
* 背景の過剰な説明、既知情報の言い換え、同一内容の重複、実装から推測した未確定事項、利用される見込みのない例や補足は追加しないでください。
* 主担当は、作業中に得たコンテキストや自分の設計意図によって「説明を追加したい側」のバイアスが生じている可能性を前提とし、自分の初稿だけで完成と判断しないでください。
* ドキュメントの新規作成または大幅な更新では、可能な限り、その実装や初稿作成を担当していないサブエージェントに添削・レビューを委任してください。
* サブエージェントには、過去の議論や主担当の思考過程を必要以上に渡さず、次の情報だけを提供してください。
- ユーザーの要件、受け入れ条件、既知の制約、対象コードや仕様は省略せずに渡す。一方で、主担当の結論、文章表現、採用したい構成など、レビュー結果を誘導する情報は必要以上に渡さない。
  * 文書の目的
  * 想定読者
  * 対象の文書
  * 正確性の確認に必要な実装、仕様、差分
* 重要な文書では、可能なら次の異なる観点を別々のサブエージェントに担当させてください。
  * 初見の読者として、理解できない箇所や不足している前提を確認する。
  * 編集者として、削除可能な説明、重複、冗長な構成を指摘する。
  * 技術レビュー担当として、実装や仕様との不一致を確認する。
* レビューでは、文章を増やす提案だけでなく、削除・圧縮・統合によって情報量を減らせないかを必ず検討してください。
* 主担当はサブエージェントの提案をそのまま採用せず、実装・仕様・ユーザーの要望と照合し、必要性と正確性を確認してから文書へ反映してください。
* 同一文書を複数のサブエージェントに直接編集させないでください。編集担当は 1 エージェントに限定し、ほかのエージェントには添削、調査、レビューのみを委任してください。
* 誤字修正や数行程度の明確な変更など、独立したレビューによる効果が小さい作業では、不要にサブエージェントを起動しないでください。

# 開発スタイル

- TDD で開発する（探索 → Red → Green → Refactoring）
- KPI やカバレッジ目標が与えられたら、達成するまで試行する。
- ユーザーの要望や要件が不明確な場合は、質問を繰り返し詳細を掘り下げ、曖昧な点を明確にしてください。

# ブランチ命名

- Git ブランチを作成する際は、変更内容に対応する Conventional Commits の type を prefix に使い、`<type>/<kebab-case-summary>` の形式にしてください（例: `feat/add-search-filter`、`fix/handle-empty-response`）。
- type は `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`remove`、`deploy`、`revert` から選んでください。
- `agent/` など、変更内容を表さない一律の prefix は使用しないでください。
- ユーザーがブランチ名を明示した場合は、その指定を優先してください。

# コミット前の確認

- CI 相当の包括的なチェックは、ファイルを変更するたびや作業途中には実行せず、予定している変更をすべて終えた後、commit の直前にまとめて実行してください。
- 作業途中では、TDD や原因の切り分けに必要な対象限定のテスト・lint・型チェックだけを実行してください。
- commit する前に、lint・型チェック・テストなどプロジェクトの CI で実行されるチェックがローカルで通ることを確認してから commit してください。
- チェックコマンドが不明な場合は、`package.json` の scripts、CI 設定（`.github/workflows/` など）、`Makefile` / `Justfile`、各言語の標準ツール設定などから推測し、該当するものを実行してください。
- チェックが失敗した場合は修正してから commit し、失敗を残したまま commit しないでください。

# 設計原則

- 最小限の変更で実装することに固執せず、設計の簡潔さと正確さを優先してください。
- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つようにしてください。
- 関心の分離を保ってください。
- 状態とロジックを分離してください。
- 可読性と保守性を重視してください。
- ユーザーから明示的な要望がない限り、後方互換性のための補助機能や代替経路の実装は行わないでください。
